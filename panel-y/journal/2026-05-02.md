### Rethinking the preview policy

- User confirmation showed that for cases with small sample counts, the preview does smooth things out noticeably.
- However, the primary workflow is "using on-waveform events as landmarks to find what to zoom into", and a preview that degrades render quality only while interacting is a poor fit.
- Decided not to adopt simple draw-point thinning or uniform sample decimation.
- When reducing draw point count, only methods that preserve the information needed for exploration are acceptable: min/max for Line, edge/change-point/density for Step.

### Performance plan v2

- Created `docs/rust_migration_phase2_performance_plan_2.md`.
- Reframed the primary strategy as a shift away from preview toward "render optimizations that don't hide events".
- Future axes:
  - Line: pixel-aware min/max envelope, overscan cache, lazy tile / LOD
  - Step: edge preservation, edge cache, dedicated LOD only when dense
  - Pan: overscan range cache to reduce regeneration
  - Multi channel: shared bucket boundaries / batched generation to cut duplicated work
- Recommended order of operations:
  - Flip preview to off-by-default / debug-only
  - Add cache hit/miss to frame timing
  - Overscan range cache
  - Shared bucket boundaries / batched generation
  - Line lazy tile / LOD
  - Step edge cache / dense LOD
  - Channel parallelism if needed

## Decisions and design notes

- Preview is a means of "degrading quality only while interacting to improve feel", but in an event-exploration waveform viewer, the risk of landmarks looking different is too large.
- Having spikes / edges / steps / outliers disappear, or having things look different mid-interaction versus when stopped, is a bigger problem than minor stutter.
- Simple decimation is rejected because it may drop short spikes and edges.
- The min/max envelope can preserve the existence of spikes and outliers even while reducing draw point count, so it's a sound default for Line rendering.
- For Step / digital signals, min/max alone makes edge positions ambiguous, so change-point / edge preservation is kept on a separate track.
- If preview is kept at all, it should be a debug / emergency toggle rather than the primary strategy.
- The `8,000,000 samples` preview threshold is not derived from memory measurements; it's a provisional heuristic that excludes medium 2M but targets large 10M.
  - Long-term, an adaptive gate based on recent normal render time or visible sample work is more natural than a fixed dataset-size threshold.

## What got stuck and how I resolved it

- After adding a preview during pan/zoom, I found it would fire even for small sample counts and degrade interaction quality.
  - Estimated load is now computed from dataset sample count, visible sample count, and channel count to narrow down when preview triggers.
  - On top of that, plan v2 demotes preview itself out of the primary strategy.
- For Line envelopes, even reducing bucket count, the cost of scanning visible samples remains.
  - Instead of a bucket-count-reducing preview, the plan is to cut the scan work itself via overscan cache, shared bucket boundaries, and lazy tile / LOD.

## Additional work: Implementing performance plan v2

### Demoting preview to debug-only

- Changed the default of `ViewState::large_preview_enabled` to `false`.
- Renamed the UI label from `Large-data preview` to `Emergency preview`.
- Preview is no longer the primary performance strategy; it remains as a debug / emergency toggle.
- Prevents the view from changing unintentionally on medium-class data or during normal event exploration.

### Overscan range cache

- Changed the envelope cache on `ChannelStore` to hold an overscan-padded cache range instead of requiring an exact match to the visible range.
- During pan, if the view range stays inside the cache range, the envelope cache is reused.
- Fixed the places that were always calling `clear_envelope_cache()` on range changes.
  - Cache is preserved during pan.
  - The context is rebuilt when zoom span changes.
- Added `EnvelopeCacheStats` so the following can be seen in frame timing / CLI:
  - envelope cache hits / misses
  - context hits / misses
  - clipped bucket count
- Added a pan cache benchmark to `--bench-phase2`.
  - It measures cache reuse for the case of panning by small amounts at a fixed window width.

### Shared bucket boundaries / batched generation

- Added `parquet_waveform::MinMaxEnvelopePlan`.
  - Bucket boundaries are built once from the time range.
  - Each channel takes its min/max using the same `EnvelopeBucketSpan`.
- Gave `EnvelopeBucket` `start_index` / `end_index` fields.
  - When clipping the overscan cache down to the visible range, only the boundary buckets need to be recomputed from raw values.
- Added `clip_min_max_envelope_to_range()`.
  - Buckets outside the overscan range are excluded from rendering.
  - Buckets straddling the visible-range boundary are recomputed from raw values.
  - Ensures Y auto range isn't pulled by outliers that lie outside the visible range.

### Line lazy tile / LOD

- Added `parquet_waveform::LineTileCache`.
  - For each channel, fixed-width `256 samples/tile` min/max tiles are lazily built.
  - Tiles are a render-time cache, kept separate from raw data.
- Tile LOD is used only for wide Line views.
  - `source_sample_count >= 500,000`
  - `bucket_size >= 512`
- The Step fallback envelope is kept off Line tiles.
  - Step edge / dense LOD is handled separately at a later stage.
- Tile-sourced bucket generation also preserves min/max, so spike / outlier presence isn't dropped.
- Added line tile cache info to the GUI cache display and frame timing.
  - tile hits / builds
  - tile memory
  - tile build time

## Decisions and design notes (additional)

- The overscan cache is effective at cutting regeneration count during pan.
  - Rendering clips to the inside of the visible range only, so the view doesn't switch between mid-pan and stopped states.
  - Y auto range can still be computed from the visible-range equivalent.
- Shared bucket boundaries are effective at reducing the fixed overhead of multi-channel display.
  - Time/index range and bucket boundaries aren't rebuilt per channel.
- Line tile / LOD has a large effect on wide large-data views.
  - The first tile build is synchronous, so the build cost lands on the large-dataset max value.
  - Subsequent passes and pan-cache cases are much improved.
- Tile memory growth across all 9 channels of the large dataset is about 9.5 MiB.
  - Small compared to the ~419.6 MiB raw cache, so within acceptable bounds.
- The current tile setup has only one level.
  - If wider or higher-resolution views become necessary, multi-level LOD or background builds will be considered.

## What got stuck and how I resolved it (additional)

- Drawing the overscan cache directly raised the concern that out-of-range outliers would bleed into Y auto range.
  - Buckets now carry their original sample index range, and when clipping to the visible range, boundary buckets are recomputed from raw values.
- Tile LOD was on the verge of being usable in the Step fallback envelope as well.
  - Now only Line rendering passes `allow_line_tile_lod = true`, separating it from the Step-side responsibilities.
- The existing pan/zoom-mixed bench made cache hits hard to see.
  - Added a fixed-window pan cache benchmark to `--bench-phase2` so the overscan cache effect can be measured.

## Additional work: Step edge cache / dense LOD

### Implementation

- Added a Step-channel edge cache to `ChannelStore`.
  - For each channel, a change-point list of `index/time/value` is lazily built.
  - The corresponding cache is dropped when the channel is reloaded.
  - All caches are dropped on dataset reset.
- Updated the Step rendering path.
  - Raw-sample Step: visible sample count is at most `MAX_EXACT_STEP_SAMPLES`.
  - Cached-edge Step: many raw samples but edge count at most `MAX_STEP_CHANGE_POINTS`.
  - Dense Step envelope: when there are too many edges.
- The cached-edge Step does a binary search of the visible range into the edge list, extracting the state just before the left edge plus the edges within the range.
- The dense Step envelope is distinguished from Line envelopes as `VisibleTraceData::DenseStepEnvelope`.
  - Rendering is a min/max ribbon.
  - The Step fallback does not use the Line tile LOD.
- Added GUI / bench surfaces.
  - Edge cache hit/build added to frame timing.
  - Step edge cache count, edge count, memory, and build time added to the cache display.
  - Dense step count, edge hit/build, edge count, and edge memory added to the bench output.

### Tests

- Added unit tests for the Step edge cache.
  - Build an accurate change-point Step by extracting a range from the edge list.
  - Carry over the prior state at the left edge of the visible range.
  - Return a dense fallback when the edge count limit is exceeded.
  - `ChannelStore` reuses the Step edge cache.
