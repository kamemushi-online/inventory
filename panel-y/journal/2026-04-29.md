## Decisions / design notes

- For the Rust port, treat `proto_3_1b`'s UI and analysis behavior as the source of truth
- `proto_3_1` has the multiconverter exe support, but for locking down the viewer spec, `proto_3_1b` takes priority
- For Phase 1, skip building a finished app — just implement this vertical slice:
  - Launch the Rust app
  - Load Parquet
  - Recognize the time column and channel columns
  - Select 1 channel
  - Render a single-row waveform
  - pan/zoom
  - min/max envelope
  - Confirm no freeze on a 90M-point-class dataset
- Analysis features should always reference raw data, not the rendering LOD
- Plot config should retain read compatibility with the current `.pyc.json`
- On small data, the Dash/Plotly version is plenty fast; the Rust version's advantage has to be shown on medium/large data
- For backend measurements, zoom re-render itself is light even on medium/large data
  - The main differences for the Rust version to compare are browser rendering, Dash communication, memory footprint, and operational consistency
- Plot config load itself took ~0.63 s on small data, but a click right after reload was flaky for automated input
  - Don't conclude "load is heavy" — keep this separate as "operation acceptance right after Dash init may be unstable"
  - For the Rust version, the state where a button is visible should match the state where it's actually clickable
- Put the Rust code at `code/rust_phase1`, not `proto_4`
  - Treating it as a "port phase" separate from the Python/Dash feature-number lineage
  - `proto_3_1b` is locked as the reference impl; Rust is a vertical-slice tech-validation effort
- For Phase 1's first Parquet step, only read schema/metadata, not the data itself
  - Before moving on to `time + 1ch` column projection, confirm we can stably get column names, types, and row-group counts
  - Even large data is light to check if we're only reading metadata
- Added the `--schema` CLI mode
  - Reproduces detection results without GUI interaction
  - Easy to extend later as the entry point for load-time / memory measurements
- For single-channel loads, use Parquet projection rather than reading all columns
  - Directly serves Phase 1's "only read needed columns; don't fall over on large data" goal
  - In this run, `time + iu` on large data fit in ~114 MiB
- Standardize value arrays on `f32`
  - The Python version also converts waveform columns to float32
  - For render data, memory efficiency wins over `f64`
  - Keep `time` as `f64` since it's the basis for search and axis math
- Implemented the first envelope as a fixed full-range bucket count, not view-range linked
  - First step is just "don't pass every point to render"
  - Next step is to re-sample based on the pan/zoom range
- 4,096 buckets is provisional
  - Draw points are ~8,000, which is near screen-width order
  - Envelope build on 10M-point large data fit in ~0.08 s, so it's a reasonable starting value for Phase 1
- Envelope bucket time is the midpoint of the bucket's first and last sample times
  - Matches the equi-time-spacing assumption of the data spec
  - Also convenient as the representative time for later range-aware LOD

## Things that tripped me up

- `pyarrow` emitted a `sysctlbyname` CPU-info warning inside the sandbox
  - Parquet load itself succeeded, so I'm calling it a non-issue for Phase 0
- Medium/large synthetic data is already generated
  - If we end up using real instrument logs, the confidentiality and anonymization policy needs to be confirmed separately
- The post-plot-config-load channel-spread-across-rows behavior is recorded as a known risk
  - For the Rust version, separate UI state updates and waveform rendering at load time to avoid the same class of Dash callback-collision issue
- For B-11 plot config load, automated clicks right after reload were sometimes missed by the Dash event layer
  - Under normal interactive conditions, the load completes in ~0.63 s
  - In benchmark results, record "processing time" and "post-init operation stability" as separate things
- B-07 zoom reset initially looked like it wasn't restoring in automated measurements, but manual re-checks couldn't reproduce it
  - Verified that the last-row X tick `0.2, 0.3, 0.4` returned to `0, 0.2, 0.4, 0.6, 0.8` on full view
  - Not flagging this as a known risk for the current Dash version
- Inside the sandbox, the initial dependency fetch for `cargo add eframe` / `cargo check` failed DNS resolution
  - With approval, accessed crates.io; after the deps were fetched, normal `cargo check` worked again
- `eframe 0.34.1`'s API differs from older samples — implementing `App::update` raised an "unimplemented `ui`" error
  - Looked at the local crate source and switched to `App::ui` + `Panel::show_inside`
- Running `cargo test` and `cargo check` in parallel caused a temporary build-directory lock wait
  - After the test finished, check completed normally too. For heavy first builds, I'll default to running them serially
- For Arrow array conversion, I first put `ArrayAccessor` as a generic bound, but the trait is implemented on the reference type, not on `PrimitiveArray<T>`, so it didn't compile
  - Switched to macro-based downcasts to concrete Arrow array types
  - Organized it as conversion to `f64` or `f32` for `Float64`, `Float32`, and signed/unsigned integers
- After reading `time + 1ch`, I'd initially added `WaveformData::value_range()` but it became unused once the envelope provided the range
  - Moved range calculation to `MinMaxEnvelope` and deleted the unused function
- Small data ended up with 4,000 buckets built against 4,096 requested
  - 100,000 points / 4,096 buckets gives a bucket size of 25, which yields 4,000 buckets
  - Implementation-wise this is fine. `requested` is the upper target; `built` is the actual draw-point basis
