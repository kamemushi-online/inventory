## Phase 2 continued: P2-06b high-density step edge preservation

### Findings

- `gate_pwm` is 1 MHz sample / 20 kHz PWM, so even mid-range zooms easily exceed `MAX_EXACT_STEP_SAMPLES = 12,000` visible samples
- On the other hand, at a display span of about 0.1s-0.3s, the change-point count is roughly 4,000-12,000, which is within range for direct Step rendering
- Falling back to min/max envelope based on sample count alone unnecessarily loses edge timing, so a change-point preservation method is needed
- Measured values:
  - `gate_pwm`
    - 0.1s: 100,001 samples / 4,000 changes -> edge-step target
    - 0.2s: 200,001 samples / 8,000 changes -> edge-step target
    - 0.3s: 300,001 samples / 12,000 changes -> edge-step target
    - 0.5s: 500,001 samples / 20,000 changes -> envelope fallback
  - `pwm_10kHz`
    - 0.2s: 20,001 samples / 4,000 changes -> edge-step target
    - 0.5s: 50,001 samples / 10,000 changes -> edge-step target
    - 1.0s: 100,001 samples / 20,000 changes -> envelope fallback

### Implementation

- Added `MAX_STEP_CHANGE_POINTS = 12,000`
- Changed the Step rendering selection order to:
  - Raw sample Step: visible sample count at or below `MAX_EXACT_STEP_SAMPLES`
  - Change-point Step: visible sample count is large but change-point count is at or below `MAX_STEP_CHANGE_POINTS`
  - Min/max envelope: when even the change-point count is too large
- Change-point Step carries the state immediately before the display-range start and retains only the sample timestamps where the value changes
- The GUI status and plot label now show the edge-step count

## Phase 2 P2-10: async loading

### Implementation

- Changed `load_selected_channel()` from synchronous UI-thread loading to spawning a worker thread
- `PanelYApp` picks up `mpsc` completion notifications at the start of each frame and only applies them to `DatasetState` / `ViewState` on completion
- At load start, a channel placeholder is added to the target row, and the plot shows `Loading waveform data...`
- Restricted risky operations during a load
  - Editing the Parquet path and reloading the schema are disabled
  - Removing a channel that is currently loading is disabled
  - Deleting a row containing a loading channel is disabled
- Already-cached channels skip the worker and are added to the row immediately
- If the same channel is already loading, no duplicate job is created; only an extra reservation to display it on another row is allowed

### Implementation

### Measurement commands

```bash
cd code/rust_phase1
cargo run --release -- --bench-phase2 ../proto_3_1b/data/panely_medium_2m_8ch.parquet
cargo run --release -- --bench-phase2 ../proto_3_1b/data/panely_large_10s_1mhz_9ch.parquet
cargo run --release -- --bench-phase2 ../proto_3_1b/data/panely_large_10s_1mhz_9ch.parquet iu iv iw gate_pwm
```

### Results summary

| case | layout | raw cache | RSS after bench | visible avg | visible max | hover |
|---|---:|---:|---:|---:|---:|---:|
| medium all 8ch | 3 rows / 8 ch | 76.3 MiB | 91.6 MiB | 8.0 ms | 22.1 ms | 0.264 us/lookup |
| large all 9ch | 3 rows / 9 ch | 419.6 MiB | 435.4 MiB | 31.3 ms | 92.5 ms | 0.439 us/lookup |
| large representative 4ch | 2 rows / 4 ch | 228.9 MiB | 244.4 MiB | 14.4 ms | 38.2 ms | 0.504 us/lookup |

### Assessment

- `panely_large_10s_1mhz_9ch.parquet` is 10M rows x 9ch, which means a 90M-channel-point measurement in total
- Even with all 9 channels of large data in the raw cache, RSS is about 435 MiB -- acceptable on the memory side
- Hover-value lookup is sufficiently lightweight and not a performance risk at this point
- For all 9 channels of large data over a wide display range, visible trace generation peaks at 92.5 ms
  - Consistent with the slight stutter during fast zoom seen in the GUI
  - At 2M-sample-equivalent it's about 32-33 ms, at 500k samples about 9 ms, at 100k samples about 1.5-1.9 ms
- As the Phase 2 completion gate, P2-12 is treated as measurement-complete
- Next performance-improvement candidates:
  - Range cache during pan/zoom, or a tile / LOD pyramid
  - Earlier decision-making for wide-range Step fallback
  - GUI-side timing measurement of `egui::Painter` shape generation

## Post-P2-12: documenting performance-improvement candidates

- Organized the outlook, risks, and alternatives for range cache / tile LOD / earlier wide-range Step fallback decisions
- New document:

- Conclusions:
  - Don't jump straight to tile / LOD; first measure GUI frame timing

  3. Earlier wide-range Step fallback decisions
  4. Channel parallelization / overscan range cache
  5. Coarse tile / LOD
